# Specs — consolidated feature behaviour contracts

One file per substantial feature: `docs/specs/<feature>.md`, the **consolidated behaviour** of that feature as shipped — its rules, contracts, invariants, verbs, transactions, edge/empty states.

The split this draws:

- **Design** (`docs/designs/*.html`) — the *surface*: layout, states, visual grammar. Regenerated by the design tool; do not cite it for behaviour.
- **Spec** (this folder) — the *behaviour contract*: what Save/Delete do, the invariants, the verbs. Hand-owned and stable, so **code comments cite the spec, not a design file**, for behaviour — in the relative-anchor form `(docs/specs/<file>.md#<anchor>)` (see `AGENTS.md`). A design reference never appears in code; if a comment needs a spec that doesn't exist, generating it is mandatory.
- **ADR** — *why* a decision was made (the spec links to it). **Explainer** (`docs/architecture/*.md`) — *how a mechanism works*. **Feature doc** (`docs/features/*.md`) — the user-facing overview.

A spec borrows [spec-kit](https://github.com/github/spec-kit)'s per-feature shape (requirements / rules / acceptance) without its toolchain. Write or update a feature's spec as part of shipping or materially changing it, and keep it current — a stale spec is worse than none. When a rule holds across many surfaces, give it one **shared** spec every instance cites, rather than restating it per surface.
